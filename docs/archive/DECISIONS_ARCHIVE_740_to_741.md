## #741 - One definition of an unidentified inflow: it is income (O.20c) (2026-09-14)

**Context.** TASKS O.20c (owner-reported, live, P1, money-visible): two unfiled deposits that look identical to a reader landed on OPPOSITE sides of the same figure. `isIncomeFlowRow` counted a positive row stored with NO category (a raw null) as INCOME via its `!t.categoryId` branch, while a positive row sitting in the taxonomy's own "we do not know" leaf, `'uncategorized'` (group `Transfers & Other`, `categories.ts:180`), failed both that branch and the Income-group test — so `monthlyFlows` SUBTRACTED it from the month's expense pool (`insights.ts:141`) while the "Spending by category" card bucketed the same row INTO spending (`spendRowCategoryId` → `'uncategorized'`). Two stores for one fact, two opposite verdicts, and a disclosure sentence (`MONTH_FLOW_BASIS`) that named the contradiction instead of resolving it.

**Measurement before the fix (the prescribed-remedy-is-a-hypothesis rule).** `scripts/audit-probes/o20c-unidentified-inflow.mts` (read-only, live Neon + raw seed) ran three ARMS per user BEFORE any code changed: (A) as shipped — null→income, `'uncategorized'`→nets spend; (B) one sign rule for every unfiled inflow — both stores are INCOME; (C) one offset rule — both stores net spending. Fidelity is exact at the server boundary: SPEND-type accounts only (demo.ts:53-54), the currency guard, and the reconciliation keep filter with its THREE positional args. **The population is the whole argument.** On the live corpus (`michael.lee.p@gmail.com`, 4,285 pooled rows): null-store positives **0 rows / $0.00**; `'uncategorized'` positives **1 row / $10,000.00**, and that row is `2026-09-04 "Funds Transfer from Brokerage -7383"` on Investor Checking — **a transfer, not income** (`isTransfer=false`; the descriptor does not match `TRANSFER_DESCRIPTOR`, and the opposite leg sits on an account type the pairing rule cannot send from, so no pair). An honest census of that store returns 0 income-looking dollars: no arm is being chosen to flatter a "deposit" that does not exist. ARM C is **unreachable on a real corpus** (0 null-store rows) — the branch it deletes is a pure-engine convenience, never a live population — so the live choice is A vs B, and B is the one that resolves the contradiction. ARM B's move: month 2026-09 income $14,419.90 → $24,419.90, expense $21,471.81 → $31,471.81, savings rate **−48.9% → −28.9%** — the row stops pretending to reduce spending. Demo seed (`user-demo`, 847 rows): unfiled positives **0**, so all three arms are byte-identical **$97,070.00 / $71,008.28** and every demo golden holds. The 161 large `'uncategorized'` positives the first draft of this probe measured were on MORTGAGE and INVESTMENT accounts — a fidelity bug (the snapshot's spend-account filter was missing), corrected before any conclusion was recorded.

**Decision — ONE definition: an unfiled inflow is INCOME, whichever store it sits in.** `isIncomeFlowRow` now admits `!t.categoryId || t.categoryId === 'uncategorized' || (t.categoryId !== 'refund' && isIncomeCategoryId(t.categoryId))`. The rule is the app's own sign rule, already applied to an unfiled OUTFLOW: an outflow nobody labelled counts as spending on its SIGN alone (`isSpendRow` resolves null→`'uncategorized'` and admits it), so the symmetric treatment of an inflow nobody labelled is income on ITS sign alone. It also fixes the real row correctly: a brokerage funding is neither income nor spending, but it must never *reduce* spending, and the only honest way to stop it doing that without a writer is to stop treating a positive it cannot classify as a negative when it does. The three consequence classes in `MONTH_FLOW_BASIS` collapse from three to two — (1) and (2) are now one rule — and the copy is re-derived, not edited: the `expense` sentence loses the "or a deposit still sitting in Uncategorized, reduces this figure" clause because that clause is now FALSE, and the `income` sentence states the unified rule. **The CARD side must agree, or the same contradiction survives on the other surface**: `isSpendRow` (reports.ts) gains the matching clause — a positive in the `'uncategorized'` placeholder (including a raw null, which resolves to it) is NOT spending, so the card can no longer let an unfiled inflow NET a category bucket down. A positive in a REAL spend category is untouched: that is the documented refund convention. `BREAKDOWN_BASIS` gains the clause naming the new drop (`an inflow nobody has filed yet`) — the sentence claims to be a COMPLETE enumeration of the predicate, so widening the predicate without widening the sentence is the silent-widening failure this constant exists to prevent. **Consumers that re-stated the same split by hand are delegated to the predicate** rather than left as a second copy: `isFallbackGuiltFreeIncomeRow` (`income-pattern.ts`) now returns `isIncomeFlowRow(t)` with its own untouchable/refund guards kept in front, so the guilt-free income pattern cannot disagree with `monthlyFlows`. The spend-side asymmetry in `discretionary-spend.ts` and `fixed-category-amounts.ts` (`!categoryId || === 'uncategorized'` skipping unfiled OUTFLOWS) is deliberately NOT touched: it is sign-scoped, excludes rather than counts, and cannot put a positive on the wrong side. **Out of scope, named not silent:** the null store's treatment by `server/backfill.ts` (which re-files nulls), and the O.20j converse leak, are untouched.

**Locked.** `tests/unit/insights.test.ts` — describe `test_regression__o20c: ONE definition of an unidentified inflow` (the placeholder store now income; the two stores agree; an ordinary spend-category refund still nets; the `'refund'` leaf and a custom category unchanged; and the income-baseline path agreeing with `monthlyFlows` on an `'uncategorized'` deposit — the delegation lock, in the same file because that is where the flow predicates are exercised). `tests/unit/month-flow-breakdown.test.ts` — the `unfiled-uncat` fixture flips to the income panel, its expense-panel absence asserted, and the parity assertion (every bar equals the plain sum of the rows listed) holds on both sides; the basis sentences re-pinned to the unified rule with the deleted clause asserted GONE via an inversion. `tests/unit/category-breakdown.test.ts` — TWO new never-listed rows (`x8` `'uncategorized'` $10,000 inflow, `x9` raw-null $600 inflow) plus the `BREAKDOWN_BASIS` completeness clause. `tests/unit/loan-payment-flow-exclusion.test.ts` — the O.18e-FU3 fixture files its refund so it still expresses the case it was written for. Probe committed as the measurement artifact.

**Gate.** `bash scripts/verify.sh` → ✅ VERIFY GREEN, exit 0; FAIL-OLD proven by stash-revert of the implementation: `tests/unit/insights.test.ts` + `tests/unit/month-flow-breakdown.test.ts` = **6 failed | 80 passed** pre-fix → green restored.

**Critic (fresh context): cycle 1 FAIL 1 P1 + 2 P2 — all fixed same-session.** P1: the decision's own "Locked." block named a test id that does not exist (`test_regression__o20c_unfiled_inflow_is_income_in_both_stores`) and claimed a lock in `tests/unit/income-pattern.test.ts`, a file the diff never touched — a fabricated lock pointer in the ledger a future session reads. Fixed by pointing at the real describe and the file where the delegation lock actually lives. P2-1: the module docblock still said "Three consequences" after the diff collapsed (1)+(2) into one rule and listed two. P2-2: the raw-null fixtures (`unfiled-null`, `x9`) exercise a store measured at 0 live rows and produced by no writer — now annotated in both files as defensive rather than left implying a live population. The critic independently reproduced the probe, the full suite, both typechecks, and FAIL-OLD (6 failed | 80 passed), and swept the entire category domain (±sign × null/'uncategorized'/180 taxonomy ids/ghost/custom) through BOTH predicates finding **no remaining opposite-side disagreement for any positive row**; it also falsified the candidate third stores (deleted customs re-file to `'uncategorized'`; `merchantCategoryId`-only rows are purchases and rejected by sign on both spend predicates; an empty-string `categoryId` is unreachable because the column is an FK).

## #740 - One discretionary definition: the creep bar classifies with the register (O.20h) (2026-09-12)

**Context.** TASKS O.20h (owner-reported, live): "Discretionary" meant two different things on screen. `detectLifestyleCreep` counted a row by the CATEGORY's `discretionary` taxonomy flag, while the register and /budgets label the same row by its SPEND CLASS (`classifySpendClass` — the reader's per-row verdict, then the recurring-bill merchant guess, then the flag; #397 "the reader's verdict on THIS row wins"). The shipped mitigation was a disclosure sentence admitting the divergence (insights.ts `creepPanelBasis`, the F2 block).

**Measurement before the fix (the prescribed-remedy-is-a-hypothesis rule).** `scripts/audit-probes/o20h-creep-definition-arms.mts` (read-only, live Neon + seed) ran both rules per user BEFORE any code changed. **Decision.** The detector selects rows on `classifySpendClass(...) === 'guilt-free'` (one definition, the register's own label): new trailing param `fixedMerchants` (empty-set default keeps every existing caller byte-identical — demo/seed ride the taxonomy flag exactly as before), `coach.ts` loads `getRecurringBillMerchantCanonicals(userId)` and carries `spendClassOverride` (already on the snapshot shape) into the engine; Ask and Money Review inherit through the same `getCoachData`. Copy: the F2 divergence disclosure is DELETED with the divergence it described (closing-a-gap-shrinks-the-disclosure rule: re-derived, not edited blind — the replacement is the positive admission rule naming the unified basis, which covers every classifier refusal by construction). Deliberately OUT of scope (recorded, not silent): `averageDiscretionaryCategorySpend` (the wealth-target cut proposals) keeps the category-grain taxonomy definition — that figure names CATEGORIES to cut, not rows, and its dial-aware copy is a different question from the per-row bar; named as the residual "second discretionary" in TASKS O.20h.
