Re-derive the authorising facts from the system that owns them; the extra call is the price of the act. Corollaries: failure direction is a design input (abstentions are the majority of the tests), a count driving copy must be computed over what will actually RENDER, a failed irreversible step falls back to the state the user can SEE, and an invariant you will not honour gets amended in the same slice (D7 → D7a + L.16), never dropped. **Extended L.17:** the same critics recorded two more paths without executing them, and both were real — a **null column read as a negative answer** (candidates selected by `institutionId`, null on every pre-#300 item, so the door was a silent no-op at exactly the banks the owner already had) and an **invariant enforced by sequence** (read-then-write, so two Link tabs both persisted); make the DECISION exclusive via a unique-keyed lease, never the outcome, and fail OPEN. - [A disclosure written for a page is false in an email](a-disclosure-written-for-a-page-is-false-in-an-email.md) — L.15 moved the duplicate-card disclosure onto six new surfaces, and every design decision came from one fact: copy qualifying a money figure carries an implicit claim about WHERE THE READER IS STANDING. "the total above" / "no amount below" are false in an email (which controls no position), a sentence quoting per-card figures is false on a surface printing only a count and a total, and every in-app variant ends by pointing at a control an email does not have. On web push, suppressing the second notification looked kind and is not — it asserts the two rows are one card, and its failure direction is a MISSED PAYMENT on a genuinely separate card, so disclose and take the redundant notification instead; the note may not claim how many notifications will arrive, since each side is filtered independently. Crons detect per run, never from a stored flag (an email carries no control to correct itself, and the detector costs no query when there is no candidate pair). Also: moving the copy module into the engine tree carried `renderSafe` with it — prove such an extraction with one character from EVERY range plus the characters just outside each (a mangled escape widens ranges), and write the class via `chr(92)`, because the heredoc wrote raw control bytes into the source twice before a byte-level check caught it. **Extended by the L.15 critic cycle (3 P1s, all the same mistake in different clothes — a property of the ORIGINAL surface baked into shared code as universal):** the positional collision breaker invented "1. X"/"2. X" on channels that number nothing, and fired on the DEFAULT shape since two connections return one provider name — whether a surface can be pointed at positionally is a fact about THE SURFACE, so make it a required argument and say "two entries are both named X" rather than manufacturing an identifier; a DEFAULTED parameter fails silent, so when an engine gains a disclosure argument grep its CALLERS (the Ask tap-through panel kept rendering both rows under a green check); and the enumerated list is where the sweep STARTS — a critic found a seventh surface, Cash Flow Radar, where the duplicate manufactured a critical dip alert and a $33,100 move instruction instead of $13,050, and a push that composes its own body never inherits a disclosure added to an `assumptions` array. Test corollary: `f(x,[]) === f(x)` compares the changed code with its own default and cannot fail — use golden literals. **And the fix for the seventh surface introduced the NEXT P1** (caught by cycle 2): the radar disclosure resolved the pair against `cashNeeded.cards` while its comment claimed to read the projection, so a PAID-OFF pair hedged a genuine overdraft warning — resolve a claim about a computed set against THAT SET, not its input, and never trust a comment about what code reads without checking it; a pure-builder abstention test hand-builds the row list and so can never catch a wiring bug. A THIRD cycle then falsified the fix to the fix: "the pair is in the projection" is not what the sentence claims ("the dip date may be earlier and the amount larger" is fixed by the worst point of the walk), so gate a disclosure on the COUNTERFACTUAL it asserts — re-walk without the suspected duplicate, speak only if the named figures move; deciding whether to speak is not adjusting what is shown, and it dissolved a separate finding for free, which is the sign a boundary is right rather than patched. Note the failure direction FLIPPED between surfaces in one week: on push, disclosing was cheap and suppressing risked a missed payment; on the radar a false hedge on a real dip makes someone under-fund and overdraft, so silence is cheap — "always disclose" is a heuristic, the failure-direction question is the rule.
- [Ask the failure-direction question per ROLE, not per class of value](failure-direction-is-per-role-not-per-value.md) — L.14 argued "a frozen balance keeps counting, we just say so" entirely over LIABILITIES (a stale card merely over-funds), and two fresh-context critics independently produced the inverse: the PAYMENT account can itself be frozen, where a balance frozen HIGH reports shortfall $0 while the real account cannot cover the autopay — the exact missed payment the rationale claimed to prevent — and Cash Flow Radar offered the frozen balance as the transfer source to move money FROM, sorted first because sources sort by size. The axis is not asset vs liability, it is FIGURE vs INSTRUCTION: a total containing a stale number is something the reader can weigh, an instruction built on one is an action whose failure is a bounced transfer and an overdrafted payment. The tell is a rationale with exactly one worked example, and it is the reassuring one; both critics could falsify it only because the argument (not just the conclusion) was written down in the code. Corollaries: resolve a disclosure against the same post-processing as the figures it qualifies (a reconciliation predecessor was announced as "still counted" after the boundary had zeroed and hidden it); "absent from the payload" is not an event unless the SUBJECT was in that payload's scope (the holdings sweep deleted an unticked brokerage's positions under its own clean-run rule, falsifying the shipped sentence); a remedy may only name a control that exists in the state the message renders in; and grep before claiming a channel is covered — a comment here claimed the copy held "in an email" for a channel never wired, and `assumptions` reaches the dashboard hero only, not /cards, Ask or the digest.
- [A disclosure is several claims wearing one sentence](a-disclosure-is-several-claims-in-one-sentence.md) — L.18's partner bug was fixed THREE times because each pass corrected one clause (subject, then possessive, then remedy) while the rest went on asserting the old assumption: a qualifying sentence is a subject, a mechanism, a possessive, an imperative, a remedy and a scope, each true or false independently, and ownership is a property of the ROW rather than of the call site's arguments. The sentence only reached the surfaces at all because the FACT was made to ride the money (`frozenSince` on the obligation) instead of a string being pasted per surface — L.14's comment claimed its `assumptions` array reached five surfaces and it reached two, the other four being four of the silent ones. Where a pure engine genuinely cannot know whose account it holds, a tri-state that names the ignorance beats a default that hides it. **Resolve a claim against the set the SURFACE renders, not the set the headline sums** — the fix for naming a card that was in no figure over-narrowed to `due` and dropped `upcoming`, whose amounts ARE the frozen balance. And mutate a disclosure in BOTH directions: silencing it failed 19 assertions, making it speak unconditionally failed 6, because a false hedge on an instruction makes a reader under-fund.
- [A subagent's green is a hypothesis until you reproduce it](a-subagents-green-is-a-hypothesis.md) — three background agents (one e2e author, two critics) each produced a correct-looking result that was wrong about the tree: the e2e agent reported 5 passed against a `.next` that predated a copy edit made after it launched, so the spec as committed could not pass; and the full unit suite, run beside those agents, reported 40 failures, then 7, in a DIFFERENT set of files each time — all phantom, every named file passing in isolation, the final clean run 4250/4250. A rotating failure set across concurrent runs is a signature of contention; the same set each run is a bug. Reproduce a delegated PASS (one grep or one spec re-run) before it enters a gate, run the gate ALONE, and prompt subagents to state what they did NOT observe — the best report here reasoned that its spec would kill the injected mutants and explicitly refused to call that a measurement. Parallelise for FINDING (the critics found 3 real P1s), serialize for PROVING. Repo corollary: `verify.sh` runs Playwright only under `VERIFY_E2E=1`, so the default gate cannot see an e2e golden drifting from the code it asserts. **Extended O.17c:** a critic can leave its mutation IN the deliverable — one was restored, the other (`canRemove={true}`, the very prop the slice existed to set) was not, and it typechecks, builds and passes every unit test because it disables only the UI half of a fence; read the full diff against your own intent before committing after ANY agent has run in the checkout, and treat a subagent's SIDE EFFECTS like its conclusions. Twin finding: a GUARD for an unreachable state is cheap and fails safe (an unfenced `deleteCustomCategory` inheriting a premise about a different action), a FEATURE for one is not (a Restore button whose copy no branch defined) — the axis is what the thing costs while it waits, not whether it is reachable.
- [A sweep bounded by the surfaces you already had in mind is not a sweep](the-narrowing-you-did-not-list.md) — L.20's thesis was "the fact is dropped at NARROWINGS" and its critic cycle found one it never listed: `ReturnMomentRadarInput`, a hand-built payload over a closed three-field type, dropped the frozen starting balance under "your cash flow looks clear" — on the one card that renders ONLY for readers returning after a week away, i.e. exactly when a feed drop happens. Also: a sentence firing on EITHER of two conditions may not describe both as true (the copy denied holding a payment the app prints elsewhere, on the commonest shape a bank sends); extracting copy out of a binary artifact makes the STRING testable and leaves the RENDERING untested (the PDF disclosure measured 861.6pt against 516pt of page and lost its scope clause and whole remedy off the right edge); a cleanup that extracts an expression must test the cases the extraction makes reachable (a MORTGAGE printed positive, so the rows disagreed with the report's own headline); and a disclosure gated on the engine's guess about what will render is gated on the wrong thing. Three parallel critics with DIFFERENT lenses: all three found the central gap, each found P1s the others missed, and one refuted a residual STATUS had recorded as open.
- [A borrowed total imports the other engine's window — share ROWS, not totals](a-borrowed-total-imports-its-window.md) — L.11(C) copied the cash-needed headline verbatim into a calendar-month budget and reserved one statement against two months' income; the verbatim-copy rule guarantees the number, never that its WINDOW fits the borrowing surface — filter the other engine's rows to your own window and sum, state each surface's window, draw an account-set boundary for the whole flow not one column, enumerate exclusions by MECHANISM, and give the untraced surface its own sentence since it cannot inherit a trace's caveat. **Extended L.11(D) (the mirror error, owner-reported "It's worse now"):** filtering to your window is not sufficient, because a window has an EDGE - seven cards dated five days past month-end made the term $0.00 and offered a whole month's income at $3,709.01/day beneath the app's own "$18,814.14 needed by Aug 5"; both figures were right about their own window and the PAIR was an instruction to overdraft.
